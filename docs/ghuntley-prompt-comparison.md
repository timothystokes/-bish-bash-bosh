## 3. Loop prompts, side by side

Ghuntley's build/QA prompts are per-product, with the product architecture inlined. Ours are generic per-mode and carry no product text.

| Aspect | ghuntley `build-prompt.md` (5209 B) | hodgepodge `prompts/forward.md` (627 B) |
|---|---|---|
| Role | "You are an AI product builder. Your job is to build a working clone of a real product from a spec that was auto-generated by inspecting the original." | "One loop iteration: do "Your item" below, then stop." |
| Inputs | Lists 7 files the agent must read: `build-spec.md`, `prd.json`, `build-progress.txt`, `CLAUDE.md`, `screenshots/…`, `clone-product-docs/` (and the shell `@`-attaches `build-spec.md`, `prd.json`, `pre-setup.md`, progress, `CLAUDE.md` in full) | Harness injects only the one unchecked `plan.md` item plus spec pointers |
| Pick work | "Read `prd.json` — pick the FIRST entry where `passes` is false." | Harness picks (`src/podge-next-item.js`); agent does "Your item" |
| One item | "**HARD STOP: Implement exactly ONE feature per invocation.** Commit, push, output promise, stop." | "do "Your item" below, then stop." |
| Tests first | "**Write tests FIRST** (TDD) … Run ONLY the new test file to confirm it fails … Do NOT run the full suite for the red step" | "Tests come first and already exist. If you add or change a test, confirm it fails by running only the new test file; run the full suite only to confirm green. No stubs." |
| Search first | not present in the build prompt | "Search before assuming something is missing. Parallel subagents for search/read/write; one for build/test." |
| Feedback loops | "`make check` … `make test` — ALL unit tests … Do NOT proceed until all green." | none in prompt; gates enforce (harness runs checks) |
| Mark done | "Update `prd.json`: set `passes` to true ONLY after all tests pass." | "Tick the item in plan.md when done. Never tick an item done to satisfy a gate. Do not weaken validation." |
| Honest tests | "**NEVER write tests that just pass.** … No `expect(true).toBe(true)`, no mocking away the thing you're testing." | "Do not weaken validation." (gates + QA step check it) |
| Spec conflict | not present | "Do not edit specs/ or tests/. On a spec/test conflict, add a "CONFLICT:" item to plan.md naming both sides and stop." |
| Progress log | "Append to `build-progress.txt`: what you built, test results, decisions, files changed." | none (harness records the step) |
| Commit/push | "`git add -A`, detailed commit message … `git push`" (agent does it) | not in prompt; harness commits |
| Stop signal | "Output `<promise>NEXT</promise>` … `<promise>COMPLETE</promise>` only if ALL features pass." (shell greps the output) | none; harness reads plan.md and gates |
| Product specifics | ~45 lines: AWS SES, RDS Postgres/Drizzle, S3, App Runner, Cloudflare, credentials, deployment, out of scope | none (all in specs/) |
| Missing tools | "Playwright and Biome are pre-configured. Do NOT reinstall them." | "Install missing tools yourself; only a missing credential blocks." |

### QA

| Aspect | ghuntley `qa-prompt.md` (4223 B) | hodgepodge `prompts/qa.md` (992 B) |
|---|---|---|
| Role | "You are an independent QA evaluator. Your job is to verify that the built clone actually works by testing every feature against the original PRD spec." | "You are an independent evaluator and a skeptic: you did not write this code and do not trust the build agent's claims; a ticked item or green suite is a claim to verify." |
| Distrust | "Do not trust that features work just because `passes: true` in prd.json. Verify everything independently." | (same idea, in the role line) |

## 5. Findings

1. Ghuntley's "tiny prompts" are only the tutorial inputs (62-208 B). His real loop prompts are 4-5 KB each and inline product architecture; his context per run is far larger than ours because whole files are `@`-attached.
2. Shared: one item per invocation, tests first with a red run of only the new file, skeptical independent QA, never weaken tests, tick done only after green.
3. Ours adds: search-before-assuming, `CONFLICT:` escape hatch, "don't tick to satisfy a gate", harness-chosen item, gates instead of promise strings, read-only QA with a structured findings schema.
4. His has that we do not: a per-iteration progress log written by the agent, in-prompt feedback commands (`make check`/`make test`), agent-driven commit/push, QA against a live original rather than specs, `<promise>` stop tokens, and a "don't reinstall pre-configured tools" line.
5. Possible follow-ups (not done, owner to decide): the progress-log idea overlaps our session log/step records; the stop-token idea is deliberately replaced by harness gates.

Claim boundary: a read-only comparison of file contents; no code changed, no loop run.
