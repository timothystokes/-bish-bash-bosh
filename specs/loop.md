# Spec: Loop (Ralph-style)
- Three independent loops (`specs/modes.md`), each driven by deterministic harness code, not the agent: `bish` (Interview Loop), `bash` (Plan Loop), `bosh` (Build Loop). One item (a question, a `specification.md` constraint/benefit, or a `plan.md` phase/task) per agent call; the harness picks it, never the agent.
- Fresh prompt each call, minimal by design (L-1/L-2, `test/next-item.test.js`): the loop's own instructions (`prompts/<loop>-loop.md`) plus that one item, never the whole store/specification/plan file. Budgets enforced by test: every `prompts/*.md` mode prompt file <= 1.8 KB; `AGENTS.md` <= 2.8 KB. Shrink prompts rather than raising budgets; enforcement lives in gates, not prompt prose.
- One native agent session carries across every item of a loop and across separate invocations of the same command for `bish`/`bash` only (`bishSession`/`bashSession` in `.bish-bash-bosh/config.yml`, each rewritten after every round/item — see `specs/adapters.md`'s opt-in `session` field). A brand-new session (no persisted token yet) also prefaces that loop's own intro prompt (`prompts/<loop>-intro.md`) once, before the loop prompt, never again for a later item or a restart that resumes the same session. `bosh` is different (see below): every build and QA call is a fresh agent context, never opting into session tracking at all.
- Prompt rules: search before assuming something is missing; parallel subagents for search/read/write, exactly one for build/test; run scoped tests after each change; record why each test exists.
- `bosh`'s Build Loop (`src/bosh-build-loop.js`) is test-driven and independently verified, not a single bare agent call per item: a fresh-context build call (`prompts/build-loop.md`, expected to write a failing test under `.bish-bash-bosh/tests/` using the bundled `.bish-bash-bosh/test-harness.js` — a pure-Node, `node:test`/`node:assert`-based black-box harness, language-agnostic since it only runs commands or makes HTTP requests against the project's own external behaviour, never imports its internals — then implement until it passes); bosh's own code (`src/bosh-test-runner.js`, never the agent's self-report) then runs the full `.bish-bash-bosh/tests/` suite as a gate; only if that passes does a fresh-context QA call follow (`prompts/qa-loop.md`, independently verifying against `interview.md`/`specification.md`/`plan.md` and the source, fixing any bug it finds directly rather than merely reporting it, never weakening or deleting a test to make it pass); bosh's code runs the full suite again as the final gate. A plan item's checkbox is ticked only once both gates have passed. A gate failure stops that `bosh` invocation immediately, leaving the item unticked so the next invocation retries it from scratch (no agent memory of the failed attempt).
- Each loop appends plain-text lines to its own log (`.bish-bash-bosh/{bish,bash,bosh}-log.md`, created empty on each command's first run): `[<ISO timestamp>] <bish|bash|bosh>: <full prompt sent>` and, only when the agent streamed reasoning text, `[<ISO timestamp>] agent: <full accumulated reasoning text>` (`src/bish-log.js`, shared by all three) — never raw JSON, never the on-screen Q/A/"Thinking..."/"Verifying..." lines. `bosh` logs both its build and QA calls this same way, in order.
- Single-run lock (`src/run-lock.js`): `bish` (incl. `--reverse`), `bash` and `bosh` take `./.bish-bash-bosh/lock` (the owner's PID, created exclusively under the project's `.bish-bash-bosh/` directory, excluded from every git status/add/clean call since it is harness-internal and never committed) after loading config and refuse with exit 2 while another live process holds it; a lock with a dead or unreadable PID is stale and replaced; the lock is released on exit. `status`/`tui` are read-only and do not lock. PID liveness is per host/PID namespace.
- Run records: the legacy agent-driven interview conversation (`src/bish-interview.js`) and `bish --reverse` (`src/bish-reverse.js`) each write their own `.bish-bash-bosh/runs/<id>/.../{transcript.txt, diff.patch, record.json}` inline (`record.json`: `{status, reason?, usage: {seconds}, changedFiles}`, written directly, not through a shared writer). `bash` and `bosh` write no run records: each item's only durable trace is its log lines (above) and the checkbox ticked in `plan.md`.
- Artifact schemas (G-6, `src/schemas/*.schema.json`, `src/config.schema.json`): JSON Schemas (draft-07) for `.bish-bash-bosh/config.yml` (`adapter`/`model` plus the two session fields above) and `record.json`. `test/artifact-schemas.test.js` validates files the writers actually produce against them with `ajv` (strict). The run lock is a plain PID file, not JSON, so it has no schema. `usage.schema.json`, `diagnosis.schema.json` and `done.schema.json` still exist for shapes no live writer produces any more (`writeIterationRecord` in `src/bosh-run-record.js`, and the old build loop's harness-derived done verification, were both tied to the removed build loop) — only unit tests still exercise them; `bish-bash-bosh status`/`tui`/`run-details.js` still read `usage.json`/`done.json`/`diagnosis.json` off disk if present, a known, structurally independent gap.
- Local execution only: invoke the phase executable directly in the project directory; the configured agent runs as a local subprocess. Container images and orchestration are not part of the current harness.
- Automatic setup (`src/bish.js`, `src/init.js` `initProject`): after argument validation, `bish` (including `--reverse`) checks for `./.bish-bash-bosh/config.yml`. Only when missing, it asks interactively for a single adapter/model, picking from numbered suggestions or typed values (`specs/adapters.md`), writes the config and commits it when possible, otherwise prints manual commit guidance. Blank input or EOF aborts with exit 2 before creating config or templates; config-write failures are reported explicitly. Existing config is validated and reused without setup prompts; invalid or unreadable config is an error, never a reason to overwrite it. There is no standalone setup command. Setup then falls through to the normal flow in the same invocation: the first interview run seeds templates and exits without an agent call, or an existing interview/reverse flow proceeds normally, sharing the same stdin reader so piped answers are not lost. There is no target repo, runtime copy or launcher scaffolding. Every command operates on the current directory; there is no `--dir` flag or global state.
