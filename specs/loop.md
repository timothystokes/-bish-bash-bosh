# Spec: Loop (Ralph-style)
- Three independent loops (`specs/modes.md`), each driven by deterministic harness code, not the agent: `-bish` (Interview Loop), `-bash` (Plan Pass, one call), `-bosh` (Build Loop). One item (a question or a `plan.md` task) per agent call, except `-bash`, which plans the whole specification in one call; the harness picks the item, never the agent.
- Fresh prompt each call, minimal by design (L-1/L-2, `test/next-item.test.js`): the loop's own instructions (`src/<command>/prompts/<command>-loop.md`) plus that one item, never the whole store/specification/plan file. Budgets enforced by test: every `prompts/*.md` mode prompt file <= 1.8 KB. Shrink prompts rather than raising budgets; enforcement lives in gates, not prompt prose.
- One native agent session carries across every item of a loop and across separate invocations of the same command for `-bish` only (`bishSession` in `.bish-bash-bosh/config.yml`, rewritten after every round — see `specs/adapters.md`'s opt-in `session` field). A brand-new session (no persisted token yet) also prefaces that loop's own intro prompt (`prompts/bish-intro.md`) once, before the loop prompt, never again for a later item or a restart that resumes the same session. `-bash` and `-bosh` are different: every plan, build and QA call is a fresh agent context, never opting into session tracking at all.
- Prompt rules: search before assuming something is missing; parallel subagents for search/read/write, exactly one for build/test; run scoped tests after each change; record why each test exists.
- `-bosh`'s Build Loop (`src/bosh/bosh-build-loop.js`) runs three fresh-context agent steps per plan item, each gated by `-bosh`'s own code (`src/bosh/bosh-test-runner.js`), never the agent's self-report: (1) WRITE TESTS (`src/bosh/prompts/bosh-tests.md`): the agent writes only the item's harness verification tests under `.bish-bash-bosh/tests/` using the bundled `.bish-bash-bosh/test-harness.js` (a pure-Node, `node:test`-based black-box harness, language-agnostic since it only runs commands or makes HTTP requests, never importing the project's internals); the harness requires at least one new or changed test file and runs just those, which must be RED (fail) before any implementation; (2) IMPLEMENT (`src/bosh/prompts/bosh-build.md`): a fresh agent implements the item and the harness runs the full suite, which must be GREEN; (3) VERIFY (`src/bosh/prompts/bosh-qa.md`): a fresh agent independently checks the work against `interview.md`/`specification.md`/`plan.md` and the source, fixing bugs directly and never weakening or deleting a test, then the full suite runs again. A step that throws or fails its gate is retried up to 5 attempts (still fresh context) with the error or failing output appended under `## Previous Failure` (tail-truncated to 4000 characters). The checkbox is ticked only once all three steps have passed; a step still failing after its last attempt stops that invocation, leaving the item unticked so the next invocation retries it from the first step. These harness tests are `-bosh`'s own verification, independent of and in addition to anything the user's objective specifies (including tests the user's project requires, which are specified and planned like any other requirement).
- Each loop appends plain-text lines to its own log (`.bish-bash-bosh/{-bish,-bash,-bosh}-log.md`, created empty on each command's first run): `[<ISO timestamp>] <persona> prompt: <full prompt sent>` and, only when the agent streamed reasoning text, `[<ISO timestamp>] <persona> response: <full accumulated reasoning text>` (`src/bish/bish-log.js`, shared by all three), so every entry says which agent role it belongs to and whether it is what was sent or what came back. Personas: `bish/bootstrap`, `bish/interviewer` (session-continuing), `bash/planner` (session-continuing), and `-bosh`'s three fresh-context roles `bosh/tester`, `bosh/builder` and `bosh/verifier`; `bosh/harness` records the harness's own gate failures between them. Never raw JSON, never the on-screen Q/A/"Thinking..."/"Verifying..." lines.
- Single-run lock (`src/shared/run-lock.js`): `-bish` (incl. `--reverse`), `-bash` and `-bosh` take `./.bish-bash-bosh/lock` (the owner's PID, created exclusively under the project's `.bish-bash-bosh/` directory, excluded from every git status/add/clean call since it is harness-internal and never committed) after loading config and refuse with exit 2 while another live process holds it; a lock with a dead or unreadable PID is stale and replaced; the lock is released on exit. PID liveness is per host/PID namespace.
- Run records: `-bish --reverse` (`src/bish/bish-reverse.js`) writes its own `.bish-bash-bosh/runs/<id>/.../{transcript.txt, diff.patch, record.json}` inline (`record.json`: `{status, reason?, usage: {seconds}, changedFiles}`, written directly, not through a shared writer). `-bash` and `-bosh` write no run records: each item's only durable trace is its log lines (above) and the checkbox ticked in `plan.md`.
- Artifact schemas (G-6, `src/schemas/*.schema.json`, `src/schemas/config.schema.json`): JSON Schemas (draft-07) for `.bish-bash-bosh/config.yml` (`adapter`/`model` plus the `bishSession` field above) and `record.json`. `test/shared/artifact-schemas.test.js` validates files the writers actually produce against them with `ajv` (strict). The run lock is a plain PID file, not JSON, so it has no schema. `usage.schema.json` and `diagnosis.schema.json` still exist for shapes no live writer produces any more (`writeIterationRecord` in `src/bosh/bosh-run-record.js` was tied to the removed build loop) — only unit tests still exercise them.
- Local execution only: invoke the phase executable directly in the project directory; the configured agent runs as a local subprocess. Container images and orchestration are not part of the current harness.
- Automatic setup (`src/bish/bish.js`, `src/shared/init.js` `initProject`): after argument validation, `-bish` (including `--reverse`) checks for `./.bish-bash-bosh/config.yml`. Only when missing, it asks interactively for a single adapter/model, picking from numbered suggestions or typed values (`specs/adapters.md`), writes the config and commits it when possible, otherwise prints manual commit guidance. Blank input or EOF aborts with exit 2 before creating config or templates; config-write failures are reported explicitly. Existing config is validated and reused without setup prompts; invalid or unreadable config is an error, never a reason to overwrite it. There is no standalone setup command. Setup then falls through to the normal flow in the same invocation: the first interview run seeds templates and exits without an agent call, or an existing interview/reverse flow proceeds normally, sharing the same stdin reader so piped answers are not lost. There is no target repo, runtime copy or launcher scaffolding. Every command operates on the current directory; there is no `--dir` flag or global state.
