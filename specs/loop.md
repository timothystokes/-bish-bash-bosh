# Spec: Loop (Ralph-style)
- `podge step` is the single iteration unit: idempotent, reads git, runs one loop, commits, emits JSON `{sha, iteration, cost, status}`.
- One item per iteration. The harness picks it: `src/next-item.js` returns the first unchecked `- [ ]` item of the target's `plan.md` (with its indented lines, capped at 1500 chars) and the open count; the agent never receives the rest of the plan.
- Fresh context each iteration, minimal by design (L-1/L-2, `test/next-item.test.js`): loop prompt + that one item + spec pointers (path and title only; the agent opens a spec when it needs it). The plan and QA prompts carry spec pointers but not plan.md. Budgets enforced by test: assembled loop prompt < 4 KB however large `plan.md` grows; build, plan, brownfield, clean-room and reverse prompts <= 120 words (Huntley's build prompt is ~100); interview, test-hardening and QA prompts <= 150 words; `AGENTS.md` <= 2.8 KB; each objective-kit file <= 1.8 KB. Shrink prompts rather than raising budgets; enforcement lives in gates, not prompt prose.
- Prompt rules: search before assuming something is missing; parallel subagents for search/read/write, exactly one for build/test; run scoped tests after each change; record why each test exists.
- Run records in the target repo: `runs/<id>/{plan.md, iterations/NNN/{prompt,transcript,diff,test.json,usage.json}, control.json}`. Each iteration dir also has `record.json` (iteration, status, changedFiles, gate results); written atomically, never overwritten (`src/run-record.js`).
- Diagnosis (H-1, `src/diagnosis.js`): every non-`ok` iteration also writes `diagnosis.json` with `{rootCause, evidence, fix, test, prevention}` (all non-empty strings, validated by the writer). The harness derives defaults from the first failing gate (or budget/agent exit) so a failure becomes a sign (prompt/spec/gate change), not a retry; the agent may override fields with a final fenced ```` ```diagnosis ```` JSON block in its transcript (last valid block wins, field by field). `runStep` returns the `rootCause` as `reason`, which `podge` prints. `ok` iterations have no `diagnosis.json`.
- Artifact schemas (G-6, `src/schemas/*.schema.json`, `src/config.schema.json`): JSON Schemas (draft-07) for `hodge.json` (explicit `build` and `qa` roles), `record.json`, `usage.json`, `diagnosis.json` and `done.json`. `test/artifact-schemas.test.js` validates files the writers actually produce against them with `ajv` (strict). The schemas describe the on-disk files; the in-code validators remain the writers' gate. The run lock is a plain PID file, not JSON, so it has no schema.
- QA (H-11/H-15, `src/qa.js`, `prompts/qa.md`): with a `qa` role in config, `podge` does not finish on a verified plan until an independent evaluator (own adapter/model) reports no findings. The evaluator is read-only: any change it makes is discarded and fails the cycle. Its reply must end with a fenced `findings` JSON array (`[]` = clean); a missing or invalid block fails the cycle, never passes it. Each finding is `{classification: violated-decision|unimplemented-requirement|decision-needing-replacement, severity: critical|high|medium|low, spec, consequence, diagnosis}` with the X-6 diagnosis shape. Findings are appended to `plan.md` as unchecked `QA-<cycle>-<n>` items under `## QA findings` (committed), so build fixes them and QA re-checks. Bounded by config `maxQaCycles` (default 5): once that many cycles are recorded and the plan is done again, the loop ends `failed`. Records: `runs/<id>/qa-N/{prompt.md,transcript.txt,findings.json,record.json}`; usage counts toward the run budget. Without a `qa` role nothing changes.
- Drivers: local Node `while` loop (`podge`); AWS Step Functions (see `cloud-driver.md`). Both only call `podge step`.
- Failures lead to tuning prompts/specs/gates, not blind retries.
- `runStep` (`src/step.js`): gates (repo, clean tree) -> baseline tests -> agent -> tests gate (no regression vs baseline; skipped for planning-only steps, see `gates.md`) -> commit. On failed/over-budget the agent's work is reverted (diff preserved in the record) and only the record is committed. Gated steps (sha null) write nothing.
- Single-run lock (`src/run-lock.js`): `hodge` (incl. `--reverse`), `podge` and `podge step` take `<sandbox>/.hodge.lock` (the owner's PID, created exclusively, outside the target repo) after loading config and refuse with exit 2 while another live process holds it; a lock with a dead or unreadable PID is stale and replaced; the lock is released on exit. `status`/`tui` are read-only and do not lock. PID liveness is per host/PID namespace.
- CLI: `podge step [--dir <sandbox>] [--run-id <id>]` (`--dir` defaults to the current directory; config is `<dir>/hodge.json`, target repo is its `targetRepo`, relative to `<dir>`; there is no `--config`, `--repo` or `--objective`) prints the step JSON to stdout; exit 0 ok, 1 failed/gated/over-budget, 2 usage/config/adapter error. The `build` role's adapter id is resolved via `src/adapters/index.js` (`defaultRegistry`).
- `podge` (`src/driver.js` `runLoop`): same flags as `step`; loops `runStep` until the target `plan.md` is done (>=1 checkbox, none unchecked) and, when specs declare `R-<spec>-<n>` requirements, `verifyDone` (`src/done.js`) agrees, or a step is failed/gated/over-budget (stops, no retry). Prints `{status, steps, reason?}`; exit 0 only when `done`. Config `requireTestPlan: true` enables the test-plan gate for `step` and `run` and the plan step (`specs/modes.md`): with specs but no `tests/PLAN.md` the first iteration writes the test plan, red tests and `plan.md`. An unchecked `CONFLICT:` plan item (the forward prompt tells the agent to record spec/test conflicts there instead of editing `specs/` or `tests/`) stops the loop as `gated` before or after a step, so no iterations are burned re-confirming it.
- Harness-derived done (X-5, `src/done.js`): applies only when specs declare requirement IDs. After the plan is fully ticked the harness runs the suite (must exit 0) and the type check, parses test names (spec reporter or TAP) and requires every requirement ID to appear in the name of at least one passing test and in none that fails (`R-a-1` is not matched by `R-a-10`), and scans non-test source for stub markers. Failure rewrites the `## Verification gaps` section of `plan.md` as unchecked `Verify:` items (ticked-but-unproven work is reopened), commits, and the loop continues until done or budget. Success or not, `runs/<run-id>/done.json` records per requirement `{id, spec, implementation, status, tests}`. The build agent cannot write `specs/`, so the harness itself sets each spec's `Implementation:` (`implemented` when all its requirements pass, `partial` when some, else `none`) and `Evidence:` (the existing tests mapped in `tests/PLAN.md`). Claim boundary: scripted adapter, unit level; test names, not coverage, are the mapping.
- `Dockerfile`: per-run container (sandbox dir mounted at `/sandbox`, the working directory; `CMD ["run"]`); agent CLIs go in the derived image `Dockerfile.agents` (pinned `copilot`, `claude`, `codex`).
- End-to-end proof: `test/e2e-toy.test.js` runs a toy target red to green through `podge` with a fake agent binary. Targets' test scripts must use a glob, not a directory, with `node --test`.
- Sandbox scaffolding: `hodgepodge init --dir <d> --adapter <id> --model <id> [--seed toy|empty|objective]` (`src/init-sandbox.js`) creates `<d>/target` (git repo, one commit, seed from `templates/toy/`, empty, or the solution-agnostic objective kit in `templates/objective/`; see `specs/modes.md`) and `<d>/hodge.json` (outside the repo; `targetRepo` is `target`, relative to `<d>`, and `hodgepodge` is `.hodgepodge`, relative to `<d>`) and `<d>/.hodgepodge` (a copy of `bin/`, `src/`, `prompts/`, `templates/`, `package.json`, `package-lock.json` and the production dependency closure from the lockfile, so the sandbox has no dependency back on the hodgepodge checkout; the launchers run it) plus executable `<d>/hodgepodge`, `<d>/hodge` and `<d>/podge` launchers so the owner can `cd <d>` and run `./hodge`, `./podge`, `./podge step`, ... (`requireTestPlan` on for toy; the objective seed's `package.json` has `scripts.test` = `node --test tests/*.test.js`). Refuses dirs inside hodgepodge and non-empty dirs. Prints `{ok, dir, repo, config, hodgepodge}`; exit 0 only when ok. The sandbox dir is the only handle afterwards: `--dir <d>` on hodge/podge/podge step/status/tui/spec-lint/ready/sync/promote defaults to the current directory, so after `cd <d>` no path flags are needed; no global state is kept.
