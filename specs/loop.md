# Spec: Loop (Ralph-style)
- Three independent loops (`specs/modes.md`), each driven by deterministic harness code, not the agent: `hodge` (Interview Loop), `gepo` (Plan Loop), `podge` (Build Loop). One item (a question, a `specification.md` constraint/benefit, or a `plan.md` phase/task) per agent call; the harness picks it, never the agent.
- Fresh prompt each call, minimal by design (L-1/L-2, `test/next-item.test.js`): the loop's own instructions (`prompts/<loop>-loop.md`) plus that one item, never the whole store/specification/plan file. Budgets enforced by test: every `prompts/*.md` mode prompt file <= 1.8 KB; `AGENTS.md` <= 2.8 KB. Shrink prompts rather than raising budgets; enforcement lives in gates, not prompt prose.
- One native agent session carries across every item of a loop and across separate invocations of the same command (`hodgeSession`/`gepoSession`/`podgeSession` in `.hodgepodge/config.yml`, each rewritten after every round/item — see `specs/adapters.md`'s opt-in `session` field). A brand-new session (no persisted token yet) also prefaces that loop's own intro prompt (`prompts/<loop>-intro.md`) once, before the loop prompt, never again for a later item or a restart that resumes the same session.
- Prompt rules: search before assuming something is missing; parallel subagents for search/read/write, exactly one for build/test; run scoped tests after each change; record why each test exists.
- Each loop appends plain-text lines to its own log (`.hodgepodge/{hodge,gepo,podge}-log.md`, created empty on each command's first run): `[<ISO timestamp>] <hodge|gepo|podge>: <full prompt sent>` and, only when the agent streamed reasoning text, `[<ISO timestamp>] agent: <full accumulated reasoning text>` (`src/hodge-log.js`, shared by all three) — never raw JSON, never the on-screen Q/A/"Thinking..." lines.
- Single-run lock (`src/run-lock.js`): `hodge` (incl. `--reverse`), `gepo` and `podge` take `./.hodgepodge/lock` (the owner's PID, created exclusively under the project's `.hodgepodge/` directory, excluded from every git status/add/clean call since it is harness-internal and never committed) after loading config and refuse with exit 2 while another live process holds it; a lock with a dead or unreadable PID is stale and replaced; the lock is released on exit. `status`/`tui` are read-only and do not lock. PID liveness is per host/PID namespace.
- Run records: the legacy agent-driven interview conversation (`src/hodge-interview.js`) and `hodge --reverse` (`src/hodge-reverse.js`) each write their own `.hodgepodge/runs/<id>/.../{transcript.txt, diff.patch, record.json}` inline (`record.json`: `{status, reason?, usage: {seconds}, changedFiles}`, written directly, not through a shared writer). `gepo` and `podge` write no run records: each item's only durable trace is its log line (above) and the checkbox ticked in `plan.md`.
- Artifact schemas (G-6, `src/schemas/*.schema.json`, `src/config.schema.json`): JSON Schemas (draft-07) for `.hodgepodge/config.yml` (`adapter`/`model` plus the three session fields above) and `record.json`. `test/artifact-schemas.test.js` validates files the writers actually produce against them with `ajv` (strict). The run lock is a plain PID file, not JSON, so it has no schema. `usage.schema.json`, `diagnosis.schema.json` and `done.schema.json` still exist for shapes no live writer produces any more (`writeIterationRecord` in `src/podge-run-record.js`, and the old build loop's harness-derived done verification, were both tied to the removed build loop) — only unit tests still exercise them; `hodgepodge status`/`tui`/`run-details.js` still read `usage.json`/`done.json`/`diagnosis.json` off disk if present, a known, structurally independent gap.
- `Dockerfile`: per-run container (the project directory bind-mounted at the working directory; `ENTRYPOINT ["podge"]`, so a container run drives the Build Loop directly); agent CLIs go in the derived image `Dockerfile.agents` (pinned `copilot`, `claude`, `codex`).
- Project init (`src/init.js` `initProject`): `hodgepodge init` asks interactively for a single adapter/model, picking from a numbered list of known choices (or typed directly; `specs/adapters.md`'s documented exception), and stores it as the one `adapter`/`model` pair `hodge`, `gepo` and `podge` all use. Writes `./.hodgepodge/config.yml` (just `adapter`/`model`; sessions are added later by each loop as it runs). Refuses if `./.hodgepodge/config.yml` already exists. There is no scaffolding: no target repo, no runtime copy, no launcher scripts; the project the owner already has is driven in place. Prints a short confirmation message naming the config path, adapter and model; exit 0 only when ok (a failure prints a one-line reason to stderr and exits 1). Every command (`hodge`, `gepo`, `podge`, `status`, `tui`, `spec-lint`, `ready`, `sync`, `promote`) then operates on the current directory; there is no `--dir` flag anywhere, so after `cd` into the project no path flags are needed and no global state is kept.
