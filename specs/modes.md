# Spec: Modes (v1)
- **Interview:** conversation to `specs/*.md`, one spec per file; emits JSON Schema/OpenAPI where applicable.
- **Forward:** specs to code + tests (core loop).
- **Reverse:** code (and running system) to specs + characterization tests; specs aligned to standards (OpenAPI, JSON Schema, EBNF grammars, example-based conformance cases).
- **Brownfield:** spec delta to change; reverse first if specs are missing.
- **Test-hardening:** strengthen tests (mutation/property tests, coverage as gate).
- **Clean-room:** rebuild from the spec bundle only; the builder never sees the source (context firewall).
- Each mode has its own tuned loop prompt in `prompts/`.
- Every objective must define its tests; the harness refuses to start loops without them.
- Mode is selected by optional config key `mode` (default `forward`); a mode with no prompt file fails loudly.
- Prompt rules shared across modes (snapshot-tested in `test/prompt-snapshots.test.js`; a prompt edit must update `test/snapshots/` via `UPDATE_SNAPSHOTS=1 npm test`): build modes (forward, brownfield, clean-room) confirm the red step by running only the new test file and run the full suite only to confirm green; every gate-checked prompt (build modes, test-hardening, interview) forbids ticking/marking done just to satisfy a gate and weakening validation; `interview` asks the owner for Out of scope per spec; `test-hardening` requires a green baseline before mutation testing, applies mutants only in a throwaway git worktree and records each surviving mutant as bad mutant / weak test / missing spec.
- With config `requireTestPlan: true`, `podge` runs spec-lint before the first step (structure only while `tests/PLAN.md` does not exist yet, including the mapping once it does) and gates (no agent call) on any problem. **Plan step:** in `forward` mode, when specs exist but `tests/PLAN.md` does not, the first `runStep` is the plan step (`prompts/plan.md` + the test-plan template + specs index + plan.md, `buildPlanPrompt`): the agent writes `tests/PLAN.md`, one red test per requirement and `plan.md`. It may only change `plan.md` and `tests/` (scope gate), skips the tests-regression gate (red by design), and is accepted only if full spec-lint (every spec and requirement ID mapped) and the test-plan gate (mapped tests exist, suite red) pass; otherwise it is `failed` and discarded. Every later step applies the test-plan gate and the normal build prompt.
- `hodge [--dir <sandbox>]` takes no objective flag: the objective is asked for on stdin as the first answer of the interview (it is always the same multi-round conversation as `hodge`; a target without an `objective/` kit gets the kit added and committed first, leaving existing files untouched). It runs the `interview` role (config must define it) with `prompts/interview.md` + the spec template. It may only write under `specs/` and `objective/`: no tests and no `tests/PLAN.md` (the plan step, see `requireTestPlan`, writes them from the specs). On agent failure, out-of-scope writes or a round that changes nothing the work is discarded (status `failed`). Spec-lint (structure only, `testPlan: false`) and the readiness check run only when the interview is expected to be over: the owner answered `done`, or the agent left no `QUESTION.md`; problems there keep the round `incomplete` and come back as the next round's gaps, never discarded. Records go to `runs/<id>/interview/` (not counted in run budget). Exit 0 only when ok.
- `hodge --reverse [--dir <sandbox>]` runs the `reverse` role (config must define it) with `prompts/reverse.md` + both templates. It may only write under `specs/` and `tests/`; it is accepted only if spec-lint passes and the characterization suite (`npm test`, injectable) is green against the unchanged source. Otherwise the work is discarded (status `failed`). Records go to `runs/<id>/reverse/`. Exit 0 only when ok.
- With config `mode: brownfield`, `runStep` (and so `podge step`/`podge`) is gated before any agent call unless `specs/` holds at least one `*.md`; the gate reason points at `hodge --reverse`. The prompt (`prompts/brownfield.md`) tells the agent to write the spec delta first, then tests, then code.
- With config `mode: test-hardening`, `runStep` is gated before any agent call unless config `hardenCommand` (string array, e.g. a coverage or mutation-score command that exits non-zero below threshold) is set. After tests pass, `checkHardeningGate` (`src/hardening-gate.js`) runs it; non-zero exit => `failed`, work reverted. The agent may only change `tests/` (and `plan.md`): a `tests-only` scope gate rejects anything else. Prompt: `prompts/test-hardening.md`. record.json gates in this mode add `tests-only` (after anti-stub) and `hardening` (after types).
- `hodgepodge clean-room --source <dir> --repo <builder-dir>` (`exportBundle`, `src/clean-room.js`) copies only `specs/` and `tests/` from the source into a fresh git repo with one root commit; it refuses a non-empty builder dir, source == builder, or a source lacking either directory. With config `mode: clean-room`, `runStep` is gated before any agent call by `checkCleanRoomGate` (firewall): the root commit may hold only `specs/`/`tests/`, specs and tests must exist, and (when given `sourceRemotes`) the builder must not have the source as a remote. Prompt: `prompts/clean-room.md`. The builder then runs the normal loop against the tests as the conformance suite.
- **Objective kit and requirements gathering** (`src/objective.js`, `src/readiness.js`, `templates/objective/`): `hodgepodge init --seed objective` copies a general, solution-agnostic kit into the target's `objective/` (PHASES.md, INTERVIEW.md, READINESS.md, BRIEF.md placeholder, OPEN-QUESTIONS.md, CONVERSATION.md) plus a starter `plan.md`, adds an `interview` role to the config and sets `requireTestPlan`. `hodge --dir <d>` (role `interview`) asks the owner for a description of the objective (written to BRIEF.md), then alternates interview rounds with the owner's answers: stage `broad` until the first spec exists (no lint), then `fine`. Questions are batched: the agent writes `objective/QUESTION.md` as `## <topic>` headings over numbered `N. <question> Default: <answer>` lines (`src/questions.js`); the owner replies `y` (all defaults) or `N: answer; M: answer` (unlisted take defaults); malformed batches are discarded and noted. Requirements gathering is a conversation, not a loop (as in the reference method, only plan and build loop). Each round drafts or updates specs from the latest answer (broad rounds too, once an answer settles a decision), adds perceived gaps as `- [ ]` lines in `objective/OPEN-QUESTIONS.md`, and ends with the agent writing one next question to `objective/QUESTION.md`; a question may end with a `Default: <answer>` line, shown with a "type y to accept the default" hint (every question also shows "type done to end the interview"), and an answer of `y`/`yes` (any case) is logged as `Accepted the proposed default: <answer>` (without a Default line `y` is an ordinary answer); the harness shows it, logs question and answer in CONVERSATION.md, commits, and starts the next round with a small prompt: pointers to PHASES/INTERVIEW/READINESS (the agent opens them when needed), BRIEF.md, the first 10 unchecked open questions and the last 1500 characters of the conversation, plus the stage (never the whole kit or conversation). Rounds that leave a question never run lint or readiness (status `incomplete`, "waiting for the owner's answer", no gaps in the prompt). An answer of `done`/`finished` (any case) is logged as `Ended the interview: the owner said done.` (CONVERSATION.md; a resumed conversation stays closing), and from then on, or after a round that left no question (a readiness claim), the prompt lists the current readiness gaps under `## Readiness gaps` and each round ends `ok` only when `checkReadiness` passes (agent fixes the gaps or asks the owner a qualifying question); an empty answer or EOF pauses (the pending question is re-asked on rerun), a claim with gaps left retries the round once (the gaps are in the prompt) and is `stalled` only when the same gaps remain, `--max-rounds` default 30 (`max-rounds`). Rounds record to `runs/<id>/interview[-N]/` and all count toward the run budget (`sumRunUsage`). Interview may write `objective/` (notes, open questions, QUESTION.md).
- **Readiness (when the conversation is enough):** `hodgepodge ready [--dir|--repo]` prints `{ready, gaps}` from `checkReadiness`: spec-lint clean for structure (`testPlan: false`: no `tests/PLAN.md` mapping; that is the plan step's output); per spec at least 3 requirements, each with exactly one "must", a failure/negative path, no vague words (fast, secure, robust, user-friendly, ...) in requirements and no non-functional requirement (latency, throughput, memory, ...) without a number, a `## Dimensions` section recording each of the ten interview dimensions as `covered` or `n/a: <reason>` (missing, unknown, duplicate or reason-less entries are gaps), a non-empty Out of scope, no TBD/TODO/FIXME/`??`/`<angle>` placeholders outside code; and no unchecked items in `objective/OPEN-QUESTIONS.md`. `podge` is gated (no agent call) until ready whenever the target has `objective/`. `templates/objective/READINESS.md` mirrors the thresholds; change both together.
