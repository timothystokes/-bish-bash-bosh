# Spec: Modes (v1)
- Three loops, one flow: `-bish` (requirements -> specs), `-bash` (specs -> plan), `-bosh` (plan -> actual files and configuration in the project root).
- Before either interview or reverse execution, `-bish` automatically asks for the adapter/model and writes config only if `.bish-bash-bosh/config.yml` is missing (`specs/loop.md`). Existing config is validated and reused, never reset. The first-interview template seeding below happens after this setup in the same invocation; setup itself makes no agent call; the README.md prerequisite below is checked first.
- `-bish --reverse`: existing code to a `.bish-bash-bosh/specification.md` describing what it does today.
- `-bish` and `-bash` each have their own tuned prompt pair in `src/<command>/prompts/`: an intro prompt (prefaced once, on a brand-new session only) and a loop prompt (prefaced on every round/item). `-bosh` is stateless instead (no intro, no session): a test-writing prompt (`src/bosh/prompts/bosh-tests.md`), an implement prompt (`src/bosh/prompts/bosh-build.md`) and a QA prompt (`src/bosh/prompts/bosh-qa.md`), each self-contained and loaded fresh on every call.
- The specification captures every requirement of the objective, non-functional ones included (any testing approaches the owner wants are part of it). The harness's own testing is not specified by these artifacts: `-bosh` applies it independently of, and in addition to, any test frameworks or suites the objective specifies. The harness refuses `-bash`/`-bosh` to start without a `specification.md`/`plan.md` respectively.
- `-bish` (always operates on the current directory, `src/bish/bish-interview-loop.js`) takes no objective flag. `-bish` (not `--reverse`) refuses to start (exit 2) unless `README.md` exists in the project root, checked before any setup prompt. The very first `-bish` run in a project with no `.bish-bash-bosh/interview.md` writes it from `src/bish/templates/bish-interview.md`, writes `.bish-bash-bosh/specification.md` from `src/bish/templates/bish-specification.md`, creates an empty `.bish-bash-bosh/bish-log.md`, then (under the run lock, no run folder) makes one fresh-session agent call with `src/bish/prompts/bish-bootstrap.md` (`src/bish/bish-bootstrap.js`) to turn `README.md` into a baseline specification and the first interview questions, and exits; it does not persist that call's session, so the Interview Loop's first round still gets `interview-intro.md`. If the agent leaves `specification.md` unchanged or writes no unprocessed question, the seeded `interview.md` and `specification.md` are removed (`bish-log.md` is kept so the failed call can be read), the run fails (exit 2) with the agent's exit status and last output and the next run repeats this step. A restart that somehow lost only `specification.md` rewrites it from the template before continuing. Once those files exist, `-bish` runs the Interview Loop. `interview.md` holds one numbered line per question, `N. [ ] Q: <question> A: <answer>`, with a single checkbox ticked only once that round has been fully handed to and processed by the agent — not as soon as the owner answers. Each round: find the first line not yet checked, show its question in colour, read one line from stdin (on a real terminal, any existing answer is shown in grey ahead of the cursor, not actually part of the editable line — Enter alone accepts it verbatim, recoloring it to the `A:` label's own color as it's accepted, any other keypress clears the whole suggestion at once and the owner's own typing then inherits that same color — see `createAsker`; piped input instead accepts an empty line as that default), write the answer back into that line (checkbox still unticked), show "Thinking..." then call the agent once with a prompt prefaced by `src/bish/prompts/bish-loop.md`'s instructions and this round's `## Question`/`## Answer` — the very first round of a brand-new session (no session persisted yet) also prefaces `src/bish/prompts/bish-loop-intro.md` above all of that, once only, never again for a later round or a restart that resumes the same session — (the agent's job: update `.bish-bash-bosh/specification.md`, add further questions with sensible defaults if it judges the spec still incomplete, then stop — by convention, not enforcement, it is expected to touch only `specification.md` and `interview.md`), streaming the agent's own live reasoning text on the line after "Thinking..." in the same grey as it arrives (the adapter contract's opt-in `onReasoning` callback — see `specs/adapters.md`; adapters with no such concept simply never call it, so nothing extra appears), tick the line's checkbox (re-reading the file first and matching by id, since the agent's own call may have appended new lines), and repeat. Every round also appends to `.bish-bash-bosh/bish-log.md`: one `[<ISO timestamp>] bish/interviewer prompt: <full prompt sent>` line for the prompt (`bish/bootstrap` for the first-run call), and, only when the agent streamed any reasoning text, one `[<ISO timestamp>] bish/interviewer response: <full accumulated reasoning text>` line for it — plain text only, never the raw JSON behind either, and never the on-screen Q/A/"Thinking..." lines (see `src/bish/bish-log.js`). One native agent session is used across every round of a `-bish` invocation and persists across separate invocations too (the `bishSession` field in `.bish-bash-bosh/config.yml`, written back after every round and named distinctly from other loops since only the Interview Loop uses it — see `specs/adapters.md`'s opt-in `session` field on the adapter request/response contract), so the agent keeps the whole conversation's context rather than starting fresh each round. EOF pauses (status `paused`, remaining count shown) so a rerun resumes where it left off; once no unanswered block is left, it reports `ok`. Exit 0 only when ok.
- `-bash` (always operates on the current directory, `src/bash/bash-plan-loop.js`) takes no objective flag. It refuses to run (exit 2) until `.bish-bash-bosh/specification.md` exists (run `-bish` first). The very first `-bash` run after that writes `.bish-bash-bosh/plan.md` from `src/bash/templates/bash-plan.md`, creates an empty `.bish-bash-bosh/bash-log.md`, then falls straight through into the Plan Loop in the same invocation (unlike `-bish`'s interview seed, nothing here needs the owner to review or answer anything first). The Plan Loop: find the first unprocessed `specification.md` item (`N. [ ] C: <constraint> B: <benefit>`; a parenthetical before either colon, such as the Interview Loop's `C (Q1):` question reference, is tolerated, and ticking an item flips only its checkbox), show its constraint in colour, show "Thinking...", call the agent once with a prompt prefaced by `src/bash/prompts/bash-loop.md`'s instructions and this item's `## Constraint`/`## Benefit` — the very first item of a brand-new session (no session persisted yet) also prefaces `src/bash/prompts/bash-intro.md` above all of that, once only, never again for a later item or a restart that resumes the same session — (the agent's job: turn the item into dependency-ordered checklist items in `.bish-bash-bosh/plan.md`, defined using a Mermaid Gantt chart (durations are the build agent's estimated minutes; sections = phases, tasks = items, `after` = `Depends`) kept in step with the numbered lines (each `Task:` starts with the chart's short name, then ` - ` and the detail), which remain what `-bosh` parses; by convention it is expected to touch only `plan.md`), tick the item's checkbox once the agent has finished, and repeat until none remain (status `ok`; unlike the Interview Loop there is no pause state, every unprocessed item is handed to the agent in one run). Every item also appends to `.bish-bash-bosh/bash-log.md`, the same shape as `bish-log.md`: `[<ISO timestamp>] bash/planner prompt: <full prompt sent>`, and, only when the agent streamed any reasoning text, `[<ISO timestamp>] bash/planner response: <full accumulated reasoning text>` (see `src/bish/bish-log.js`, reused as-is). One native agent session carries across every item and across separate `-bash` invocations (the `bashSession` field in `.bish-bash-bosh/config.yml`, named distinctly from `bishSession` since only the Plan Loop uses it). Exit 0 only when ok.
- `-bosh` (always operates on the current directory, `src/bosh/bosh-build-loop.js`) takes no objective flag. It refuses to run (exit 2) until `.bish-bash-bosh/plan.md` exists (run `-bash` first). The first `-bosh` run creates an empty `.bish-bash-bosh/bosh-log.md`, seeds `.bish-bash-bosh/test-harness.js` from `src/bosh/templates/bosh-test-harness.js` (a pure-Node, `node:test`/`node:assert`-based black-box verification harness: `runCommand` and `httpRequest` helpers plus a re-exported `assert`, language-agnostic since it only exercises the project's external behaviour, never its internals) and creates `.bish-bash-bosh/tests/`, then runs the Build Loop. `plan.md`'s build items are numbered lines, `<n>. [ ] P: <phase> T: <task> S: <specification ids> D: <item numbers, comma separated, or None>` (the long `Phase:`/`Task:`/`Depends:` labels are also accepted; `S` and `D` are optional; the Plan Loop's agent numbers items from 1, orders them so dependencies come first and keeps every `Depends` consistent) (distinct from the Plan Loop's own `N. [ ] C: ... B: ...` items, which the Plan Loop turns into these as it processes each one): find the first unchecked line whose dependencies are all ticked (a dependency on a nonexistent number is ignored), show its phase and task in colour; if unticked items remain but none is ready (a cycle), stop with status `blocked` (exit 1) naming the unmet dependencies; ticking flips only the checkbox. Unlike `-bish`/`-bash`, `-bosh` never opts into session tracking — every call below is a fresh agent context with no memory of any earlier call, relying instead on `plan.md`'s ticked items and the project's own files to know what already exists. For that one item, each step a fresh agent call retried up to 3 attempts with the failure under `## Previous Failure`: (1) show "Writing tests...", the agent writes only the item's harness verification tests under `.bish-bash-bosh/tests/` (`bosh-tests.md`); -bosh's code (`src/bosh/bosh-test-runner.js`) requires new or changed test files and that they run RED; (2) show "Implementing...", the agent implements the item (`bosh-build.md`) and -bosh's code requires the full suite GREEN; (3) show "Verifying...", the agent independently checks the work against `interview.md`/`specification.md`/`plan.md` and the source, fixing bugs directly (`bosh-qa.md`), and the full suite runs again. Only once all three have passed does it re-read `plan.md` and match the recorded line by its index before ticking it (tolerant of concurrent edits: a line that no longer matches is left alone rather than erroring), and repeat until none remain (status `ok`; no pause state, every unprocessed item is handed to the agent in one run, unless a step giving up stops it first). Every agent call also appends to `.bish-bash-bosh/bosh-log.md`, the same shape as `bish-log.md`/`bash-log.md`, labelled `bosh/tester`, `bosh/builder` or `bosh/verifier` (`prompt`/`response`), with the harness's own gate failures as `bosh/harness`. Exit 0 only when ok, 1 when a gate failure stopped the run, 2 when plan.md is missing or another error occurs.
- `-bish --reverse` (always operates on the current directory) runs the configured `adapter`/`model` with `src/bish/prompts/bish-reverse.md` + the specification template. It may only write `.bish-bash-bosh/specification.md`; it is accepted only if that file holds at least one well-formed item. Otherwise the work is discarded (status `failed`). Records go to `.bish-bash-bosh/runs/<id>/reverse/`. Exit 0 only when ok.
