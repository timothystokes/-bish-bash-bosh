# Spec: Modes (v1)
- Three loops, one flow: `hodge` (requirements -> specs), `gepo` (specs -> plan), `podge` (plan -> actual files and configuration in the project root).
- `hodge --reverse`: code (and running system) to specs + characterization tests; specs aligned to standards (OpenAPI, JSON Schema, example-based conformance cases).
- `hodgepodge clean-room --source <dir> --repo <builder-dir>` (`exportBundle`, `src/clean-room.js`) copies only `specs/` and `tests/` from the source into a fresh git repo with one root commit, so the loops above can be rerun there without the builder ever seeing the source; it refuses a non-empty builder dir, source == builder, or a source lacking either directory.
- `hodge` and `gepo` each have their own tuned prompt pair in `prompts/`: an intro prompt (prefaced once, on a brand-new session only) and a loop prompt (prefaced on every round/item). `podge` is stateless instead (no intro, no session): a build prompt (`prompts/build-loop.md`) and a QA prompt (`prompts/qa-loop.md`), each self-contained and loaded fresh on every call.
- Every objective must define its tests; the harness refuses `gepo`/`podge` to start without a `specification.md`/`plan.md` respectively.
- `hodge` (always operates on the current directory, `src/hodge-interview-loop.js`) takes no objective flag. The very first `hodge` run in a project with no `.hodgepodge/interview.md` only writes it from `templates/interview-template.md`, writes `.hodgepodge/specification.md` from `templates/specification-template.md`, creates an empty `.hodgepodge/hodge-log.md`, and exits: no lock, no run folder, no adapter resolved, nothing else; a restart that somehow lost only `specification.md` rewrites it from the template before continuing. Once those files exist, `hodge` runs the Interview Loop. `interview.md` holds one numbered line per question, `N. [ ] Q: <question> A: <answer>`, with a single checkbox ticked only once that round has been fully handed to and processed by the agent — not as soon as the owner answers. Each round: find the first line not yet checked, show its question in colour, read one line from stdin (on a real terminal, any existing answer is shown in grey ahead of the cursor, not actually part of the editable line — Enter alone accepts it verbatim, recoloring it to the `A:` label's own color as it's accepted, any other keypress clears the whole suggestion at once and the owner's own typing then inherits that same color — see `createAsker`; piped input instead accepts an empty line as that default), write the answer back into that line (checkbox still unticked), show "Thinking..." then call the agent once with a prompt prefaced by `prompts/interview-loop.md`'s instructions and this round's `## Question`/`## Answer` — the very first round of a brand-new session (no session persisted yet) also prefaces `prompts/interview-intro.md` above all of that, once only, never again for a later round or a restart that resumes the same session — (the agent's job: update `.hodgepodge/specification.md`, add further questions with sensible defaults if it judges the spec still incomplete, then stop — by convention, not enforcement, it is expected to touch only `specification.md` and `interview.md`), streaming the agent's own live reasoning text on the line after "Thinking..." in the same grey as it arrives (the adapter contract's opt-in `onReasoning` callback — see `specs/adapters.md`; adapters with no such concept simply never call it, so nothing extra appears), tick the line's checkbox (re-reading the file first and matching by id, since the agent's own call may have appended new lines), and repeat. Every round also appends to `.hodgepodge/hodge-log.md`: one `[<ISO timestamp>] hodge: <full prompt sent>` line for the prompt, and, only when the agent streamed any reasoning text, one `[<ISO timestamp>] agent: <full accumulated reasoning text>` line for it — plain text only, never the raw JSON behind either, and never the on-screen Q/A/"Thinking..." lines (see `src/hodge-log.js`). One native agent session is used across every round of a `hodge` invocation and persists across separate invocations too (the `hodgeSession` field in `.hodgepodge/config.yml`, written back after every round and named distinctly from other loops since only the Interview Loop uses it — see `specs/adapters.md`'s opt-in `session` field on the adapter request/response contract), so the agent keeps the whole conversation's context rather than starting fresh each round. EOF pauses (status `paused`, remaining count shown) so a rerun resumes where it left off; once no unanswered block is left, it reports `ok`. Exit 0 only when ok.
- `gepo` (always operates on the current directory, `src/gepo-plan-loop.js`) takes no objective flag. It refuses to run (exit 2) until `.hodgepodge/specification.md` exists (run `hodge` first). The very first `gepo` run after that writes `.hodgepodge/plan.md` from `templates/plan-template.md`, creates an empty `.hodgepodge/gepo-log.md`, then falls straight through into the Plan Loop in the same invocation (unlike `hodge`'s interview seed, nothing here needs the owner to review or answer anything first). The Plan Loop: find the first unprocessed `specification.md` item (`N. [ ] C: <constraint> B: <benefit>`), show its constraint in colour, show "Thinking...", call the agent once with a prompt prefaced by `prompts/plan-loop.md`'s instructions and this item's `## Constraint`/`## Benefit` — the very first item of a brand-new session (no session persisted yet) also prefaces `prompts/plan-intro.md` above all of that, once only, never again for a later item or a restart that resumes the same session — (the agent's job: turn the item into dependency-ordered checklist items in `.hodgepodge/plan.md`; by convention it is expected to touch only `plan.md`), tick the item's checkbox once the agent has finished, and repeat until none remain (status `ok`; unlike the Interview Loop there is no pause state, every unprocessed item is handed to the agent in one run). Every item also appends to `.hodgepodge/gepo-log.md`, the same shape as `hodge-log.md`: `[<ISO timestamp>] gepo: <full prompt sent>`, and, only when the agent streamed any reasoning text, `[<ISO timestamp>] agent: <full accumulated reasoning text>` (see `src/hodge-log.js`, reused as-is). One native agent session carries across every item and across separate `gepo` invocations (the `gepoSession` field in `.hodgepodge/config.yml`, named distinctly from `hodgeSession` since only the Plan Loop uses it). Exit 0 only when ok.
- `podge` (always operates on the current directory, `src/podge-build-loop.js`) takes no objective flag. It refuses to run (exit 2) until `.hodgepodge/plan.md` exists (run `gepo` first). The first `podge` run creates an empty `.hodgepodge/podge-log.md`, seeds `.hodgepodge/test-harness.js` from `templates/test-harness.js` (a pure-Node, `node:test`/`node:assert`-based black-box verification harness: `runCommand` and `httpRequest` helpers plus a re-exported `assert`, language-agnostic since it only exercises the project's external behaviour, never its internals) and creates `.hodgepodge/tests/`, then runs the Build Loop. `plan.md`'s build items are dash-bulleted lines, `- [ ] Phase: <phase> Task: <task>` (distinct from the Plan Loop's own `N. [ ] C: ... B: ...` items, which the Plan Loop turns into these as it processes each one): find the first unchecked line, show its phase and task in colour. Unlike `hodge`/`gepo`, `podge` never opts into session tracking — every call below is a fresh agent context with no memory of any earlier call, relying instead on `plan.md`'s ticked items and the project's own files to know what already exists. For that one item: (1) show "Thinking...", call the agent once with a prompt prefaced by `prompts/build-loop.md`'s instructions and this item's `## Phase`/`## Task` (the agent's job: write a failing test under `.hodgepodge/tests/` using the bundled harness, then implement until it passes; by convention it is expected to work only within that item's scope); (2) podge's own code (`src/podge-test-runner.js`, never the agent's self-report) runs the full `.hodgepodge/tests/` suite as a gate — a failure stops this `podge` invocation immediately (status `failed`), leaving the item unticked so a later invocation retries it from scratch; (3) if that passed, show "Verifying...", call the agent once more with a prompt prefaced by `prompts/qa-loop.md`'s instructions and the same item (the agent's job: independently check the implementation against `interview.md`/`specification.md`/`plan.md` and the source, fixing any bug it finds directly rather than merely reporting it, never weakening or deleting a test to make it pass); (4) podge's code runs the full suite again as the final gate, same failure handling as step 2. Only once both gates have passed does it re-read `plan.md` and match the recorded line by its index before ticking it (tolerant of concurrent edits: a line that no longer matches is left alone rather than erroring), and repeat until none remain (status `ok`; no pause state, every unprocessed item is handed to the agent in one run, unless a gate failure stops it first). Every agent call also appends to `.hodgepodge/podge-log.md`, the same shape as `hodge-log.md`/`gepo-log.md`. Exit 0 only when ok, 1 when a gate failure stopped the run, 2 when plan.md is missing or another error occurs.
- `hodge --reverse` (always operates on the current directory) runs the configured `adapter`/`model` with `prompts/reverse.md` + both templates. It may only write under `specs/` and `tests/`; it is accepted only if spec-lint passes and the characterization suite (`npm test`, injectable) is green against the unchanged source. Otherwise the work is discarded (status `failed`). Records go to `.hodgepodge/runs/<id>/reverse/`. Exit 0 only when ok.
- **Requirements gathering, old agent-driven conversation (`src/hodge-objective.js`, `src/readiness.js`, `src/hodge-questions.js`; superseded above for `hodge`'s CLI entry point by the no-agent Interview Loop and its own `.hodgepodge/interview.md` format — this module is still unit-tested directly but no longer reachable from the CLI):** the configured `adapter`/`model` come from `.hodgepodge/config.yml`, written by `hodgepodge init`. Once `.hodgepodge/interview.md` exists (seeded from the template by the first `hodge` run, above), `hodge` asks the owner for a description of the objective and bootstraps it as question 1 in `.hodgepodge/interview.md` (pre-answered, already specified: it is context, not a spec decision), then alternates interview rounds with the owner's answers: stage `broad` until the first spec exists (no lint), then `fine`. **Questions are managed by code, never by the agent** (`src/hodge-questions.js`): `.hodgepodge/interview.md` is a code-owned store of `<id> - Answered: [ |x]; Specified: [ |x]; Topic: <topic>; Q: <question>; Default: <default>` lines (`; A: <answer>` replaces `Default:` once answered, `; Spec: <spec>` is appended once a spec records the decision). Code picks the next batch (unanswered questions in store order, at most 3 topics and 8 questions), shows it as `## <topic>` headings over numbered `N. <question> Default: <answer>` lines, and takes the owner's replies one line at a time: `N: answer` overrides a default (unlisted questions keep theirs), accumulated until `ok` continues with the remaining defaults; `done`/`finished` accepts every remaining default across the whole interview and starts closing. Answers are recorded in the store, then committed. The round prompt carries the objective (question 1's answer, shown every round), **only this round's answers keyed by question id** (`Q<id> [topic] question: answer`), the count of questions still to ask, the stage and, when closing, the readiness gaps; never the store or whole files. The agent drafts or updates specs from the answers and finishes by writing `.hodgepodge/response.json`: `{"resolved":[{"id":N,"spec":"specs/x.md"}],"gaps":[{"topic","question","default"}]}` (a missing file is an empty response; invalid JSON or a resolved id that was not answered this round leaves the round `incomplete`, work kept, answers still pending, the reason in the next prompt). Code then updates the store: resolved ids become specified with their spec, answered ids not resolved are asked again with the owner's answer as the default, gaps become new questions (a repeated question text is dropped). A paused conversation resumes by re-deriving the same batch from the store; the in-memory closing flag is not persisted across a pause (it only lives for the current `hodge` invocation) and re-derives itself within a round or two of resuming, as soon as no question is left to ask. Rounds with questions left to ask never run lint or readiness (status `incomplete`, "waiting for the owner's answer", no gaps in the prompt). After `done`, or after a round that leaves no question to ask (a readiness claim), the prompt lists the current readiness gaps under `## Readiness gaps` and each round ends `ok` only when `checkReadiness` passes (the agent fixes the gaps or reports them as gaps for the owner); an empty answer or EOF pauses, a claim with gaps left retries the round once (the gaps are in the prompt) and is `stalled` only when the same gaps remain, `--max-rounds` default 30 (`max-rounds`). Rounds record to `.hodgepodge/runs/<id>/interview[-N]/` and their usage is summed for visibility with other run usage (`sumRunUsage`; there is no run-wide cap). Interview may write `.hodgepodge/notes.md` and `.hodgepodge/response.json` (consumed by code, never committed).
- **Readiness (when the conversation is enough):** `hodgepodge ready [--repo <dir>]` (defaults to the current directory) prints `{ready, gaps}` from `checkReadiness`: spec-lint clean for structure (`testPlan: false`: no `tests/PLAN.md` mapping); per spec at least 3 requirements, each with exactly one "must", a failure/negative path, no vague words (fast, secure, robust, user-friendly, ...) in requirements and no non-functional requirement (latency, throughput, memory, ...) without a number, a `## Dimensions` section recording each of the ten interview dimensions as `covered` or `n/a: <reason>` (missing, unknown, duplicate or reason-less entries are gaps), a non-empty Out of scope, no TBD/TODO/FIXME/`??`/`<angle>` placeholders outside code; and every question's line checked in `.hodgepodge/interview.md` (this last check still assumes the old `hodge-questions.js` store format; not yet reconciled with the Interview Loop's `N. [ ] Q: ... A: ...` format above). Neither `gepo` nor `podge` is gated by readiness today; `gepo` is gated only by `specification.md` existing, `podge` only by `plan.md` existing.
