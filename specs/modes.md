# Spec: Modes (v1)
- **Interview:** conversation to `specs/*.md`, one spec per file; emits JSON Schema/OpenAPI where applicable.
- **Forward:** specs to code + tests (core loop).
- **Reverse:** code (and running system) to specs + characterization tests; specs aligned to standards (OpenAPI, JSON Schema, example-based conformance cases).
- **Brownfield:** spec delta to change; reverse first if specs are missing.
- **Test-hardening:** strengthen tests (mutation/property tests, coverage as gate).
- **Clean-room:** rebuild from the spec bundle only; the builder never sees the source (context firewall).
- Each mode has its own tuned loop prompt in `prompts/`.
- Every objective must define its tests; the harness refuses to start loops without them.
- Mode is selected by optional config key `mode` (default `forward`); a mode with no prompt file fails loudly.
- Prompt rules shared across modes (snapshot-tested in `test/prompt-snapshots.test.js`; a prompt edit must update `test/snapshots/` via `UPDATE_SNAPSHOTS=1 npm test`): build modes (forward, brownfield, clean-room) confirm the red step by running only the new test file and run the full suite only to confirm green; every gate-checked prompt (build modes, test-hardening, interview) forbids ticking/marking done just to satisfy a gate and weakening validation; `interview` asks the owner for Out of scope per spec; `test-hardening` requires a green baseline before mutation testing, applies mutants only in a throwaway git worktree and records each surviving mutant as bad mutant / weak test / missing spec.
- With `requireTestPlan` on (always, for the real `podge`/`podge step` commands — `specs/gates.md`), `podge` runs spec-lint before the first step (structure only while `tests/PLAN.md` does not exist yet, including the mapping once it does) and gates (no agent call) on any problem. **Plan step:** in `forward` mode, when specs exist but `tests/PLAN.md` does not, the first `runStep` is the plan step (`prompts/plan.md` + the test-plan template + specs index + plan.md, `buildPlanPrompt`): the agent writes `tests/PLAN.md`, one red test per requirement and `plan.md`. It may only change `plan.md` and `tests/` (scope gate), skips the tests-regression gate (red by design), and is accepted only if full spec-lint (every spec and requirement ID mapped) and the test-plan gate (mapped tests exist, suite red) pass; otherwise it is `failed` and discarded. Every later step applies the test-plan gate and the normal build prompt, with no scope restriction.
- `hodge` (always operates on the current directory, `src/hodge-interview-loop.js`) takes no objective flag. The very first `hodge` run in a project with no `.hodgepodge/interview.md` only writes it from `templates/interview-template.md`, writes `.hodgepodge/specification.md` from `templates/specification-template.md`, and exits: no lock, no run folder, no adapter resolved, nothing else; a restart that somehow lost only `specification.md` rewrites it from the template before continuing. Once those files exist, `hodge` runs the Interview Loop. `interview.md` holds one numbered line per question, `N. [ ] Q: <question> A: <answer>`, with a single checkbox ticked only once that round has been fully handed to and processed by the agent — not as soon as the owner answers. Each round: find the first line not yet checked, show its question in colour, read one line from stdin (on a real terminal, any existing answer is shown in grey ahead of the cursor, not actually part of the editable line — Enter alone accepts it verbatim, recoloring it to the `A:` label's own color as it's accepted, any other keypress clears the whole suggestion at once and the owner's own typing then inherits that same color — see `createAsker`; piped input instead accepts an empty line as that default), write the answer back into that line (checkbox still unticked), show "Thinking..." then call the agent once with a prompt prefaced by `prompts/interview-loop.md`'s instructions and this round's `## Question`/`## Answer` — the very first round of a brand-new session (no session persisted yet) also prefaces `prompts/interview-intro.md` above all of that, once only, never again for a later round or a restart that resumes the same session — (the agent's job: update `.hodgepodge/specification.md`, add further questions with sensible defaults if it judges the spec still incomplete, then stop — by convention, not enforcement, it is expected to touch only `specification.md` and `interview.md`), streaming the agent's own live reasoning text on the line after "Thinking..." in the same grey as it arrives (the adapter contract's opt-in `onReasoning` callback — see `specs/adapters.md`; adapters with no such concept simply never call it, so nothing extra appears), tick the line's checkbox (re-reading the file first and matching by id, since the agent's own call may have appended new lines), and repeat. One native agent session is used across every round of a `hodge` invocation and persists across separate invocations too (the `interviewSession` field in `.hodgepodge/config.yml`, written back after every round and named distinctly from other phases since only the Interview Loop uses it — see `specs/adapters.md`'s opt-in `session` field on the adapter request/response contract), so the agent keeps the whole conversation's context rather than starting fresh each round. EOF pauses (status `paused`, remaining count shown) so a rerun resumes where it left off; once no unanswered block is left, it reports `ok`. Exit 0 only when ok.
- `hodge --reverse` (always operates on the current directory) runs the configured `adapter`/`model` with `prompts/reverse.md` + both templates. It may only write under `specs/` and `tests/`; it is accepted only if spec-lint passes and the characterization suite (`npm test`, injectable) is green against the unchanged source. Otherwise the work is discarded (status `failed`). Records go to `.hodgepodge/runs/<id>/reverse/`. Exit 0 only when ok.
- With config `mode: brownfield`, `runStep` (and so `podge step`/`podge`) is gated before any agent call unless `specs/` holds at least one `*.md`; the gate reason points at `hodge --reverse`. The prompt (`prompts/brownfield.md`) tells the agent to write the spec delta first, then tests, then code.
- With config `mode: test-hardening`, `runStep` is gated before any agent call unless config `hardenCommand` (string array, e.g. a coverage or mutation-score command that exits non-zero below threshold) is set. After tests pass, `checkHardeningGate` (`src/podge-hardening-gate.js`) runs it; non-zero exit => `failed`, work reverted. The agent may only change `tests/` (and `plan.md`): a `tests-only` scope gate rejects anything else. Prompt: `prompts/test-hardening.md`. record.json gates in this mode add `tests-only` (after anti-stub) and `hardening` (after types).
- `hodgepodge clean-room --source <dir> --repo <builder-dir>` (`exportBundle`, `src/clean-room.js`) copies only `specs/` and `tests/` from the source into a fresh git repo with one root commit; it refuses a non-empty builder dir, source == builder, or a source lacking either directory. With config `mode: clean-room`, `runStep` is gated before any agent call by `checkCleanRoomGate` (firewall): the root commit may hold only `specs/`/`tests/`, specs and tests must exist, and (when given `sourceRemotes`) the builder must not have the source as a remote. Prompt: `prompts/clean-room.md`. The builder then runs the normal loop against the tests as the conformance suite.
- **Requirements gathering, old agent-driven conversation (`src/hodge-objective.js`, `src/readiness.js`, `src/hodge-questions.js`; superseded above for `hodge`'s CLI entry point by the no-agent Interview Loop and its own `.hodgepodge/interview.md` format — this module is still unit-tested directly but no longer reachable from the CLI):** the configured `adapter`/`model` come from `.hodgepodge/config.yml`, written by `hodgepodge init`. Once `.hodgepodge/interview.md` exists (seeded from the template by the first `hodge` run, above), `hodge` asks the owner for a description of the objective and bootstraps it as question 1 in `.hodgepodge/interview.md` (pre-answered, already specified: it is context, not a spec decision), then alternates interview rounds with the owner's answers: stage `broad` until the first spec exists (no lint), then `fine`. **Questions are managed by code, never by the agent** (`src/hodge-questions.js`): `.hodgepodge/interview.md` is a code-owned store of `<id> - Answered: [ |x]; Specified: [ |x]; Topic: <topic>; Q: <question>; Default: <default>` lines (`; A: <answer>` replaces `Default:` once answered, `; Spec: <spec>` is appended once a spec records the decision). Code picks the next batch (unanswered questions in store order, at most 3 topics and 8 questions), shows it as `## <topic>` headings over numbered `N. <question> Default: <answer>` lines, and takes the owner's replies one line at a time: `N: answer` overrides a default (unlisted questions keep theirs), accumulated until `ok` continues with the remaining defaults; `done`/`finished` accepts every remaining default across the whole interview and starts closing. Answers are recorded in the store, then committed. The round prompt carries the objective (question 1's answer, shown every round), **only this round's answers keyed by question id** (`Q<id> [topic] question: answer`), the count of questions still to ask, the stage and, when closing, the readiness gaps; never the store or whole files. The agent drafts or updates specs from the answers and finishes by writing `.hodgepodge/response.json`: `{"resolved":[{"id":N,"spec":"specs/x.md"}],"gaps":[{"topic","question","default"}]}` (a missing file is an empty response; invalid JSON or a resolved id that was not answered this round leaves the round `incomplete`, work kept, answers still pending, the reason in the next prompt). Code then updates the store: resolved ids become specified with their spec, answered ids not resolved are asked again with the owner's answer as the default, gaps become new questions (a repeated question text is dropped). A paused conversation resumes by re-deriving the same batch from the store; the in-memory closing flag is not persisted across a pause (it only lives for the current `hodge` invocation) and re-derives itself within a round or two of resuming, as soon as no question is left to ask. Rounds with questions left to ask never run lint or readiness (status `incomplete`, "waiting for the owner's answer", no gaps in the prompt). After `done`, or after a round that leaves no question to ask (a readiness claim), the prompt lists the current readiness gaps under `## Readiness gaps` and each round ends `ok` only when `checkReadiness` passes (the agent fixes the gaps or reports them as gaps for the owner); an empty answer or EOF pauses, a claim with gaps left retries the round once (the gaps are in the prompt) and is `stalled` only when the same gaps remain, `--max-rounds` default 30 (`max-rounds`). Rounds record to `.hodgepodge/runs/<id>/interview[-N]/` and their usage is summed for visibility with other run usage (`sumRunUsage`; there is no run-wide cap). Interview may write `.hodgepodge/notes.md` and `.hodgepodge/response.json` (consumed by code, never committed).
- **Readiness (when the conversation is enough):** `hodgepodge ready [--repo <dir>]` (defaults to the current directory) prints `{ready, gaps}` from `checkReadiness`: spec-lint clean for structure (`testPlan: false`: no `tests/PLAN.md` mapping; that is the plan step's output); per spec at least 3 requirements, each with exactly one "must", a failure/negative path, no vague words (fast, secure, robust, user-friendly, ...) in requirements and no non-functional requirement (latency, throughput, memory, ...) without a number, a `## Dimensions` section recording each of the ten interview dimensions as `covered` or `n/a: <reason>` (missing, unknown, duplicate or reason-less entries are gaps), a non-empty Out of scope, no TBD/TODO/FIXME/`??`/`<angle>` placeholders outside code; and every question's line checked in `.hodgepodge/interview.md` (this last check still assumes the old `hodge-questions.js` store format; not yet reconciled with the Interview Loop's `N. [ ] Q: ... A: ...` format above). `podge` is gated (no agent call) until ready whenever the project has started an interview (`.hodgepodge/interview.md` exists).
