# Spec: Repo model
- Bish-Bash-Bosh holds the harness only. It never holds delivered work.
- The package and management command are `bish-bash-bosh`; the phase commands are `bish` (requirements/specs), `bash` (plan), and `bosh` (build). Invoke the planner by its explicit executable path to avoid confusing it with the system bash shell; do not prepend the harness's `bin/` to `PATH`.
- Every command operates directly on the current working directory: the project being built. There is no separate sandbox dir and no `--dir` flag; `.bish-bash-bosh/config.yml` (config: adapter, model) lives under the project's `.bish-bash-bosh/` directory, alongside the project's own files.
- Repo gate: the harness must refuse to run if the project directory is bish-bash-bosh's own checkout (the harness never builds itself by accident).
- Per-step commits go to the project's own branch; humans review completed work (`bish-bash-bosh promote` opens a PR, never merges) before it is promoted further. This applies to `bish --reverse` and the legacy agent-driven interview conversation, the only loops that still touch git directly. `bish`'s Interview Loop, `bash`'s Plan Loop and `bosh`'s Build Loop commit nothing themselves: each only writes `.bish-bash-bosh/*.md`/project files directly to disk, leaving commits to the owner.
- Before a loop starts, `bish`'s automatic setup commits only a newly created config when possible; otherwise it prints manual commit guidance. This setup commit does not include interview templates, other loop output or unrelated staged owner changes; those changes remain staged.
- Promotion beyond that PR review is deferred (likely a traditional CD pipeline).
- Local execution: commands and their agent subprocesses run directly in the current project with the user's permissions, without container isolation. The cloud driver (`specs/cloud-driver.md`) remains deferred with no infrastructure implementation.
